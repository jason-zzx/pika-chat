# i18n Guidelines

> Cookie-based `next-intl` setup: catalog rules, locale resolution, the
> switcher pattern, testing, the server error-key contract, the ESLint
> regression guard, and the add-a-locale checklist.
> Core landed in `09-10-i18n-core`; screens migrated in `09-10-i18n-ui`;
> the guard + locale checklist landed in `09-10-i18n-guard`.

---

## Library and mode

- `next-intl@4.14.2` (pinned), cookie-based, **no i18n routing** — no
  `[locale]` segment, no middleware, URLs unchanged.
- `next.config.ts` wraps the config with `createNextIntlPlugin()` **without an
  argument** (auto-discovers `src/i18n/request.ts`). Never pass a path —
  Turbopack rejects absolute paths.
- Type-safe keys come from `src/global.d.ts` augmenting the **v4 `AppConfig`
  interface** (`Locale` + `Messages`). `IntlMessages` is the v3-era name and
  silently does nothing.

## Catalogs

One catalog per locale, at the repo root: `messages/en.json` (source of truth)
and `messages/zh-CN.json`.

- Every key added in `en.json` gets its `zh-CN` translation **in the same
  change** — no translation backlog.
- Namespaces are fixed and dotted; do not rename established ones:
  `RootLayout`, `Layout`, `Common`, `Settings.*`, `Admin`, `Assistant`, `Auth`,
  `Account`, `Chat.*`, `Topic`, `Provider`, `Search`, `Errors`, `Validation`.
  The app shell lives under `Layout.*` (`sidebar`, `settingsNav`, `userMenu`,
  `theme`, `locale`, `tree` for the assistant tree / mobile drawer — all
  migrated); the `Assistant` namespace covers the assistant editor/delete
  dialogs and the emoji picker; `Provider` / `Search` cover the settings
  screens for provider and web-search configuration.
- Keys are nested paths, not literal dotted keys: write
  `"Errors": { "topic": { "notFound": "…" } }` and call `t("topic.notFound")`
  — a JSON key containing `.` is unreachable.
- ICU for interpolation: `"switchTo": "Switch to {theme}"`. Value names are
  alphanumeric + underscore only — locale codes used as ICU values must avoid
  dashes (`zh_CN`).
- Editing `messages/en.json` changes the type of every `t()` call: add or fix
  the other locale in the same commit and run `pnpm typecheck`.
- Cross-repo copy (assistant names, topic titles, user names) is data, not
  catalog text.

## Locale resolution and persistence

`src/i18n/locales.ts` owns the constants: `locales` (`en`, `zh-CN`),
`DEFAULT_LOCALE`, `LOCALE_COOKIE_NAME` (`NEXT_LOCALE`), `LOCALE_LABELS`
(native self-labels — intentionally never translated), `matchAcceptLanguage`.

`src/i18n/request.ts` resolves, in order:

1. `NEXT_LOCALE` cookie (validated against `locales`),
2. `Accept-Language` (q-weighted; exact tag then base-language prefix, so
   `zh`/`zh-Hans` → `zh-CN`),
3. `en`.

Cookie writes happen **only in a Server Action** (`src/i18n/actions.ts`,
`setLocaleCookie`) — one-year `path=/`, `SameSite=Lax`, mirroring
`THEME_COOKIE_MAX_AGE`. A `document.cookie` write does **not** re-render the
server tree (next-intl #2162) and must not be used for the switcher. The
action is invoked from `src/components/layout/LocaleControl.tsx`; Next
re-renders the route after the action, so the UI updates without a manual
reload while the URL stays unchanged.

## Adding a locale

Adding a locale is catalog + registration work — **no component edits**.
Exact steps (dry-run verified with a throwaway `ja`):

1. `src/i18n/locales.ts` — add the code to `locales` and its native
   self-label to `LOCALE_LABELS`. The switcher (`LocaleControl` maps over
   `locales`) and `Accept-Language` matching pick it up automatically.
2. Add `messages/<code>.json`, starting from a copy of `en.json`; keep it
   key-identical to `en.json` (see Common pitfalls).
3. `src/i18n/defaults.ts` — import the new catalog and add the locale to
   `DEFAULT_MESSAGES`, referencing the catalog's `Chat.newTopic` and
   `Assistant.defaultName` (these values are also written to the DB as
   sentinels, so translate them now — they must be unique per locale).
4. `src/test-utils/render-with-intl.tsx` — add the catalog to `MESSAGES`.
5. Run `pnpm typecheck && pnpm test`.

What TypeScript/tests force (observed in the dry-run):

- `pnpm typecheck` lists the missing locale at every `Record<Locale, …>`
  site: `LOCALE_LABELS`, `DEFAULT_MESSAGES`, and the test-utils `MESSAGES`
  (the latter two were exactly the compile errors the dry-run surfaced).
- `src/i18n/defaults.test.ts` requires each locale's `Chat.newTopic` to be
  distinct — a verbatim `en.json` copy fails (`expected 2 to be 3`) until
  `Chat.newTopic` + `Assistant.defaultName` are really translated.
- `src/i18n/request.ts` (dynamic catalog import) and the switcher need no
  changes — the locale appears end-to-end by registration alone.

## Using translations

| Context | API |
|---|---|
| Server Component (async), `generateMetadata` | `getTranslations(namespace)` from `next-intl/server` |
| Server Component (non-async), shared component | `useTranslations(namespace)` from `next-intl` |
| Client Component | `useTranslations(namespace)` from `next-intl` |
| Route Handler (streaming error text) | `getTranslations(namespace)` from `next-intl/server` |

Rules:

- Namespace at the call site is the dotted path, e.g.
  `useTranslations("Settings.General")`; the returned `t` takes relative keys.
- Hooks cannot be called from `async` components — use the `get*` server APIs
  there.
- Keep `"use client"` at the narrowest component that needs it; a non-async
  component that only calls `useTranslations` can stay a Server Component.
- `<html lang>` comes from `getLocale()` in `src/app/layout.tsx`; localized
  title/description from `generateMetadata` + `getTranslations("RootLayout")`.
  Static `export const metadata` cannot read the request locale.
- `<NextIntlClientProvider>` is rendered in the root layout **outside**
  `AppProviders` with **no props** — a server-rendered provider inherits
  `locale/messages/now/timeZone/formats` from `request.ts`; a client-rendered
  provider (tests) requires `locale` + `messages` explicitly.

## Server error localization (R5 contract)

The wire shape is `{ error: { code, messageKey, params?, details? } }` — no
English `message` field. `code` stays the machine-readable branch key.

- `AppError(code, status, messageKey, params?, details?)` in
  `src/server/errors.ts`. `messageKey` is an `Errors` catalog key derived from
  the catalog type (`AppErrorMessageKey` in `src/lib/api/error-contract.ts`),
  so throw sites are compile-checked. `Error.message` is set to the key for
  debug/stack traces, never shown to users.
- `withErrorHandling` (`src/app/api/_lib/with-error-handling.ts`) is the only
  place the envelope is built: `AppError` → its fields; `ZodError` →
  `VALIDATION_FAILED` + `messageKey: "validation.failed"` +
  `details.fieldErrors[field] = { key, params? }` (keys relative to the
  `Validation` namespace); anything else → `INTERNAL` +
  `messageKey: "unexpected"` + `details.requestId`.
- Server logs stay English; provider/upstream text stays verbatim.
- Client resolution: `apiErrorMessage(error, t, fallbackKey)` with
  `t = useTranslations("Errors")` — known key → `t(key, params)`, unknown key →
  `t("generic")`, non-envelope error → `t(fallbackKey)`. Fallback keys live in
  `Errors.actions.*` and are passed as the third argument, never as English
  text.
- Per-field validation details (`details.fieldErrors`) carry `Validation`
  keys, but no screen renders them yet — resolve them with
  `useTranslations("Validation")` (unknown key → `t("invalid")`) at the first
  form that displays field errors.
- Streaming: the stream carries text, so `/api/chat` and the regenerate route
  resolve `providerErrorText(description, t)` against the request locale —
  our wrapper copy comes from the `Errors` catalog (`kind: "key"`), upstream
  provider detail passes through verbatim (`kind: "verbatim"`). `stop` uses the
  same envelope (not a stream).
- Dynamic-key typing: wire keys are plain strings. The single sanctioned
  widening is `asDynamic` in `src/lib/api/error-message.ts`, guarded by
  next-intl's own `t.has` runtime lookup. Do not add more casts — route new
  dynamic keys through these helpers.

## Testing

Use `renderWithIntl` from `src/test-utils/render-with-intl.tsx` for any `.tsx`
test whose tree renders a translated component (otherwise next-intl throws
"context from `NextIntlClientProvider` was not found").

```tsx
import { renderWithIntl } from "@/test-utils/render-with-intl";

renderWithIntl(<SettingsNav showUsers />);                      // en
renderWithIntl(<SettingsNav showUsers />, { locale: "zh-CN" }); // localized copy
```

- The wrapper loads the **real catalogs**, fixes `timeZone="UTC"`, and accepts
  `now` for deterministic date output. Assert against catalog text, not
  hardcoded duplicates.
- `rerender` needs `wrapWithIntl` around the replacement tree — the provider
  is not persisted across RTL rerenders.
- Locale-resolution logic is pure and unit-tested in `src/i18n/locales.test.ts`
  (`unit-node`); error resolution is unit-tested in
  `src/lib/api/error-message.test.ts` and
  `src/app/api/_lib/with-error-handling.test.ts`. Keep non-UI tests
  provider-free.

## Regression guard (ESLint)

`eslint-plugin-i18next@6.1.5` is an error-level guard in `eslint.config.mjs`;
`pnpm lint` (which lints `src/`) fails on new hardcoded copy.

- `i18next.configs["flat/recommended"]` plus a calibrated block for
  `src/**/*.{ts,tsx}` with `mode: "jsx-only"` — JSX text, JSX attributes,
  and string literals inside JSX expression containers are all checked.
- `jsx-attributes.exclude` is the calibration seam: attribute names whose
  values can never be rendered copy (styling, form wiring, generated ids,
  `data-*` markers, design-system/positioning enum tokens, `defaultValue`).
  Anything that renders text (`placeholder`, `title`, `alt`, `aria-label`,
  children) stays checked. `value` is deliberately **not** excluded — on
  `<input type="submit|button|reset">` it renders as the button label — so
  literal select wire values (`<SelectItem value="user">`) carry an inline
  disable instead. Excludes need a reason in the config; never widen
  `words.exclude` globally to silence a single hit.
- `callees.exclude` re-lists the plugin defaults (the option replaces, not
  merges, the default object) plus translator aliases (`t` + PascalCase,
  e.g. `tErrors`, `tCommon` — keep that naming convention) and helpers whose
  string arguments are keys/mode tokens (`apiErrorMessage`, `canAdminister`,
  `setEditor`, `toggleSection`).
- `src/**/*.test.ts(x)` disable the rule — test fixtures are not
  user-facing.
- One file allowlist: `src/components/provider/vendor-icons/marks.tsx`
  (SVG `<title>` = vendor brand names, proper nouns).
- Policy when the guard fires: **extend the catalogs, don't add excludes.**
  Migrate the copy (en + zh together) in the same change. An exclude is only
  for a *class* of values that can never be rendered copy — never for a
  single hit; one-off non-copy tokens use
  `// eslint-disable-next-line i18next/no-literal-string -- reason`, and a
  file that is non-translatable by nature gets a file allowlist with a
  reason comment. The rule stays `error`; do not downgrade it.
- Accepted gap: the plugin's default `words` excludes let ALL-CAPS strings
  (`OK`) and punctuation/emoji pass — review covers those; keep them out of
  JSX text going forward.

## Common pitfalls

- A missing `messages` entry for a "server" locale is a runtime `t()` error;
  source catalogs must be key-identical.
- Message keys can contain `.` (nesting) but the *namespace segment* cannot.
- `t.has(key)` is the only safe check for dynamic keys; a plain `try/catch`
  around `t()` hides real catalog gaps.
- Do not add a global `timeZone` to `request.ts` without a product decision —
  it changes user-visible times.
- `messages/en.json` is a type source: a key renamed there breaks every call
  site at `pnpm typecheck`, which is the point.
- Third-party widgets carry their own copy. Base UI `Select` renders the raw
  `value` in the trigger unless you pass `items={{ value: label }}` or give
  `SelectValue` children — localized options alone are not enough (see
  `AdminUsersScreen`). frimousse's emoji picker needs `locale` (map `zh-CN` →
  `zh`) for localized category headers and emoji names, plus a `placeholder`
  override for its search box (its default is `Search…`).
