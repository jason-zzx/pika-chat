# Database Guidelines

> Drizzle ORM against embedded SQLite (`better-sqlite3`). Schema, migrations,
> ownership isolation, synchronous transactions, and credential handling.

---

## Engine

SQLite only (`better-sqlite3` + `drizzle-orm/better-sqlite3`). There is no
multi-dialect abstraction — SQLite-specific features (`WITHOUT ROWID`,
triggers updating `message_file_refs`, `json_each`, `json_set`, deterministic
UDFs, and `{ behavior: "immediate" }` write transactions) are used directly.

Deployment runs the app container directly (`DATABASE_PATH=/data/files/pika-chat.db`
in Docker, `<userData>/local/pika-chat.db` in desktop local mode), with optional
one-time PostgreSQL boot import (`src/server/db/import-postgres.ts`) when a
previous PostgreSQL connection is configured against an empty SQLite database.
The connection comes from `resolveDatabaseUrl()` (`src/server/env.ts`):
`DATABASE_URL`, else one assembled from the discrete `POSTGRES_*` variables that
PostgreSQL-based releases accepted, so an upgrade needs no config change. These
variables are legacy-only: compose files, `.env.example` and the README do not
mention them. A source whose columns differ from the v0.4.0 – v0.4.2 schema
(migration 0028, shared by v1.0.0-rc.1) is refused with "upgrade to v0.4.2 first".

## Schema conventions

One file per domain under `src/server/db/schema/`. Add `schema/index.ts` as a
re-export barrel when a second domain file appears; until then `drizzle.config.ts`
points at the single schema file.

| Rule | Value |
|---|---|
| Table name | `snake_case`, plural — `chat_messages` |
| Column name | `snake_case` — `created_at` |
| Drizzle export | `camelCase`, plural — `chatMessages` |
| Primary key | `text` id, application-generated UUIDv7 (`newId()`); URL-exposed entities use prefixed short ids instead — see below |
| Timestamps | Integer epoch milliseconds (`timestampMs` / `timestampMsDefaultNow` via `unixepoch('subsec') * 1000`) |
| Every table | `created_at`, and `updated_at` where mutable |
| Enums | Inline `text({ enum: [...] })`, validated by Zod at the boundary |

> **Exception — adapter-owned tables.** When a third-party adapter writes the
> rows (Better Auth's `two_factors`), the table mirrors that library's declared
> fields exactly and adds only the `id` the adapter fills from
> `advanced.database.generateId`. Do not add `created_at` / `updated_at`
> bookkeeping the adapter never writes — those columns would silently lie. See
> [Auth Guidelines](./auth-guidelines.md).

UUIDv7 over serial: ids appear in URLs and will later cross an API boundary to
a mobile client, where sequential integers leak volume and invite enumeration.
UUIDv7 over UUIDv4: it keeps index locality, which matters for the message
table's append-heavy pattern.

Short prefixed ids over UUIDv7 for URL segments: assistants and topics are the
ids users see in the address bar, so they are minted as `agt_` / `tpc_` + 12
base62 chars (~71 bits) by `newAssistantId()` / `newTopicId()` in
`src/lib/id.ts`, inserted through `insertWithShortId`
(`src/server/db/short-id-insert.ts`) which re-mints on a primary-key collision.
Rows created before this convention keep their UUIDv7 ids — id columns are
`text` and nothing validates the format. Everything else (messages, files,
auth tables) stays on UUIDv7.

Integer epoch milliseconds over SQLite text dates: the value is timezone-free
(self-hosted instances run in every timezone and the container's TZ is not
something we control), compares and indexes as a plain integer, and maps to a JS
`Date` exactly. Keyset cursors therefore carry the millisecond integer, never an
ISO string — see [Topic List Pagination](./topic-list-pagination.md).

## Migrations

Generated by drizzle-kit, committed to the repo, applied automatically by
`src/instrumentation.ts` on every boot (Docker, `pnpm dev` / `next start`, and
desktop local mode alike; there is no separate migrate step or script).

```bash
pnpm db:generate      # after editing schema/, produces a migration
pnpm db:migrate       # optional: applies pending migrations without booting the app
```

The baseline is `0000`; history before the SQLite switch lives in git only.
`0001_message_file_refs_triggers.sql` is a custom migration
(`drizzle-kit generate --custom`) holding the `message_file_refs` triggers,
which drizzle-kit does not model: a later `pnpm db:generate` neither reproduces
nor drops them. Changing what the triggers match (the `/api/files/` URL prefix,
`FILE_URL_PREFIX`) needs a new custom migration that recreates both triggers —
see [Chat Attachments](./chat-attachments.md).

Rules:

- Never hand-edit a migration that has been applied anywhere. Write a new one.
- Never edit schema files without generating the matching migration in the same
  commit. A schema/migration split across commits leaves the tree unbootable.
- Columns added after the SQLite switch (e.g. `topics.temporary`, migration
  `0002`) do not exist in a v0.4.2 PostgreSQL source: exclude them from
  `IMPORT_TABLES` in `src/server/db/import-postgres.ts` (and `finalSchemaColumns`
  in `import-postgres.test.ts`) so boot imports keep working and leave those
  columns at their SQLite defaults.
- A migration must apply cleanly from an **empty** database. Self-hosters
  install fresh far more often than we upgrade.
- Destructive changes get their own migration, separate from additive ones, so
  a bad deploy can stop halfway without data loss.

## Ownership isolation

This is a multi-user instance. Most tables are user-owned.

**Every query touching a user-owned table filters by the owner.** There is no
"admin sees everything" shortcut baked into a query — an admin-wide read is a
separate, explicitly named service function.

```ts
// Good
const rows = await db
  .select()
  .from(topics)
  .where(and(eq(topics.userId, actor.userId), eq(topics.id, topicId)));
```

```ts
// Bad — fetch-then-check. The row already left the database, and the check is
// one early return away from being forgotten.
const row = await db.select().from(topics).where(eq(topics.id, topicId));
if (row.userId !== actor.userId) throw new ForbiddenError();
```

Filter in the `WHERE` clause. A missing row and a forbidden row should be
indistinguishable to the caller anyway — see
[Error Handling](./error-handling.md).

## Provider configuration: the visibility rule

Provider configs live in **one** table keyed by owner and visibility, not in
separate admin and user tables.

| Creator | `visibility` | Usable by |
|---|---|---|
| admin | `shared` | every user on the instance |
| admin | `private` | that admin only |
| regular user | `private` (forced) | that user only |

Two rules follow, and both are load-bearing:

**1. `visibility = 'shared'` is an admin-only transition, enforced in the
service layer.** The Route Handler receives arbitrary JSON; a regular user can
POST `{"visibility":"shared"}` regardless of what the UI renders. The service
coerces non-admin writes to `private`. Do not implement this as a validation
error — coercion is friendlier and closes the hole just as firmly.

**2. Model availability is a derived query, not a stored list.** The models a
user may select are the models of admin `shared` configs, union the models of
that user's own configs. Put this resolution in exactly one service function.
Chat, assistant defaults, and the model picker must all call it, or they will
drift and users will see models they cannot actually use.

## Credential encryption

Provider API keys are encrypted at rest with a server-side secret from the
environment (authenticated encryption — AES-256-GCM or equivalent; never plain
AES-CBC, never a bare hash).

- The plaintext key never leaves the service layer. API responses return a
  masked form (last four characters), never the key itself.
- Decryption happens at the moment of the provider call and the plaintext is
  not retained.
- **Operator-facing consequence that must reach the deployment docs**: losing
  the encryption secret makes every stored credential permanently
  unrecoverable. It is not derivable from the database.

## Model catalog storage

Catalog metadata (context window, output limit, modalities, capabilities) comes
from models.dev, but `ollama`, `vllm`, `llamacpp`, and generic OpenAI-compatible
relays are absent from it — exactly the self-hosted long tail. Research:
`.trellis/tasks/08-31-providers/research/model-metadata-sources.md`.

Therefore:

- Every metadata field is **nullable and overridable per model row**. Do not
  model it as a foreign key into an immutable catalog table.
- Keep catalog-sourced values distinguishable from user-entered ones (a
  `source` discriminator, or separate columns). Otherwise a catalog refresh
  silently clobbers the operator's hand-tuned values — a bug that surfaces
  weeks later as "why did my context limit change".
- Store `fetched_at` so the UI can tell the operator how stale the catalog is.

## Transactions and Single-Writer SQLite

The Node process runs a single `better-sqlite3` connection on `globalThis.sqlite`
with `WAL`, `synchronous = NORMAL`, `foreign_keys = ON`, and `busy_timeout = 5000`:

- **Transactions are synchronous (`db.transaction(fn, { behavior: "immediate" })`).**
  `better-sqlite3` throws if a transaction callback returns a Promise. Thread the
  synchronous `tx` (`DbTransaction` / `DbExecutor`) into helpers called inside
  it and finish queries with `.get()` / `.all()` / `.run()`; a helper called
  inside a transaction is synchronous (callers outside one may still `await`
  its value). `immediate` takes the write lock at `BEGIN`, so another process
  on the file (the `sqlite3` CLI, a backup) waits through `busy_timeout`
  instead of failing a read-to-write lock upgrade mid-transaction. Reads outside
  a transaction keep `await db.select()…`.
- **The event loop is the lock.** On the single connection no other query can
  run while a synchronous callback executes, so whole transactions are
  serialized. That is what replaced every PostgreSQL `SELECT … FOR UPDATE`:
  one active generation per topic, exclusive queued-to-running claims, and
  delete-vs-finalize ordering hold because the check and the write sit in one
  `immediate` transaction. Do not add row-lock emulation. Calling `getDb()`
  inside a transaction is harmless (same connection), but threading `tx`
  stays the convention.
- **Never perform network I/O inside a transaction.** The callback cannot
  `await`, so this is structural: run read-only pre-checks as plain reads, do
  the LLM/S3/HTTP I/O outside any transaction, then repeat the authoritative
  check and write in one short `immediate` transaction. A read-only check
  does not need an `immediate` transaction of its own. Any large
  synchronous query blocks the whole server; keep hot paths on indexes
  (`message_file_refs`, `topics_assistant_list_idx`).
- **The PostgreSQL boot import is the one exception**
  (`src/server/db/import-postgres.ts`, called from `register()` after the boot
  migration and before `startGenerationRunner()`). It sets
  `foreign_keys = OFF`, then holds a manual `BEGIN IMMEDIATE … COMMIT` open
  across awaited PostgreSQL reads, and writes the `postgres_import` marker in
  that same transaction. This is safe only because Next awaits `register()`
  before serving requests, so nothing else touches the connection meanwhile.
  Do not move the import later in boot, run it lazily, or reuse the pattern
  elsewhere.
- **Hand-written SQL migrations must separate multiple statements with
  `--> statement-breakpoint`** so Drizzle's SQLite migrator executes each chunk
  as its own statement.

## Forbidden

- String-interpolated SQL. Use Drizzle's query builder, or `sql` with bound
  parameters.
- `db` imported outside `src/server/`.
- Queries in Route Handlers.
- `SELECT *` into an API response. Project explicitly; it is how key columns
  and password hashes escape.
- Cascading deletes on message data without an explicit product decision.
- `async` transaction callbacks, `.for("update")`, and network I/O inside a
  transaction (see above).
- PostgreSQL-only syntax in `sql` fragments (`::` casts, `ilike`, `jsonb_*`,
  `@>`, `regexp_replace`, `now()`). Use the SQLite equivalent (`like … escape`,
  `json_each`, `json_set`, application timestamps).
