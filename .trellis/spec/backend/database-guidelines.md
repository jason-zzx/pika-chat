# Database Guidelines

> Drizzle ORM against PostgreSQL. Schema, migrations, ownership isolation, and
> credential handling.

---

## Engine

PostgreSQL only. There is no SQLite path and no dual-dialect abstraction, so
dialect-specific features are fair game: `jsonb`, full-text search, and
`pgvector` when a later phase needs it.

Deployment is Docker Compose — the app container plus a `postgres` container.

---

## Schema conventions

One file per domain under `src/server/db/schema/`. Add `schema/index.ts` as a
re-export barrel when a second domain file appears; until then `drizzle.config.ts`
points at the single schema file.

| Rule | Value |
|---|---|
| Table name | `snake_case`, plural — `chat_messages` |
| Column name | `snake_case` — `created_at` |
| Drizzle export | `camelCase`, plural — `chatMessages` |
| Primary key | `text` id, application-generated UUIDv7 (`newId()`); URL-exposed entities use prefixed short ids instead — see below |
| Timestamps | `timestamp with time zone`, not naive |
| Every table | `created_at`, and `updated_at` where mutable |
| Enums | PostgreSQL enum via `pgEnum`, not free-text |

> **Exception — adapter-owned tables.** When a third-party adapter writes the
> rows (Better Auth's `two_factors`), the table mirrors that library's declared
> fields exactly and adds only the `id` the adapter fills from
> `advanced.database.generateId`. Do not add `created_at` / `updated_at`
> bookkeeping the adapter never writes — those columns would silently lie. See
> [Auth Guidelines](./auth-guidelines.md).

UUIDv7 over serial: ids appear in URLs and will later cross an API boundary to
a mobile client, where sequential integers leak volume and invite enumeration.
UUIDv7 over UUIDv4: it keeps index locality, which matters for the message
table's append-heavy pattern.

Short prefixed ids over UUIDv7 for URL segments: assistants and topics are the
ids users see in the address bar, so they are minted as `agt_` / `tpc_` + 12
base62 chars (~71 bits) by `newAssistantId()` / `newTopicId()` in
`src/lib/id.ts`, inserted through `insertWithShortId`
(`src/server/db/short-id-insert.ts`) which re-mints on a primary-key collision.
Rows created before this convention keep their UUIDv7 ids — id columns are
`text` and nothing validates the format. Everything else (messages, files,
auth tables) stays on UUIDv7.

`timestamptz` over `timestamp`: self-hosted instances run in every timezone and
the container's TZ is not something we control.

## Migrations

Generated by drizzle-kit, committed to the repo, applied on deploy.

```bash
pnpm db:generate      # after editing schema/, produces a migration
pnpm db:migrate       # applies pending migrations
```

Rules:

- Never hand-edit a migration that has been applied anywhere. Write a new one.
- Never edit schema files without generating the matching migration in the same
  commit. A schema/migration split across commits leaves the tree unbootable.
- A migration must apply cleanly from an **empty** database. Self-hosters
  install fresh far more often than we upgrade.
- Destructive changes get their own migration, separate from additive ones, so
  a bad deploy can stop halfway without data loss.

## Ownership isolation

This is a multi-user instance. Most tables are user-owned.

**Every query touching a user-owned table filters by the owner.** There is no
"admin sees everything" shortcut baked into a query — an admin-wide read is a
separate, explicitly named service function.

```ts
// Good
const rows = await db
  .select()
  .from(topics)
  .where(and(eq(topics.userId, actor.userId), eq(topics.id, topicId)));
```

```ts
// Bad — fetch-then-check. The row already left the database, and the check is
// one early return away from being forgotten.
const row = await db.select().from(topics).where(eq(topics.id, topicId));
if (row.userId !== actor.userId) throw new ForbiddenError();
```

Filter in the `WHERE` clause. A missing row and a forbidden row should be
indistinguishable to the caller anyway — see
[Error Handling](./error-handling.md).

## Provider configuration: the visibility rule

Provider configs live in **one** table keyed by owner and visibility, not in
separate admin and user tables.

| Creator | `visibility` | Usable by |
|---|---|---|
| admin | `shared` | every user on the instance |
| admin | `private` | that admin only |
| regular user | `private` (forced) | that user only |

Two rules follow, and both are load-bearing:

**1. `visibility = 'shared'` is an admin-only transition, enforced in the
service layer.** The Route Handler receives arbitrary JSON; a regular user can
POST `{"visibility":"shared"}` regardless of what the UI renders. The service
coerces non-admin writes to `private`. Do not implement this as a validation
error — coercion is friendlier and closes the hole just as firmly.

**2. Model availability is a derived query, not a stored list.** The models a
user may select are the models of admin `shared` configs, union the models of
that user's own configs. Put this resolution in exactly one service function.
Chat, assistant defaults, and the model picker must all call it, or they will
drift and users will see models they cannot actually use.

## Credential encryption

Provider API keys are encrypted at rest with a server-side secret from the
environment (authenticated encryption — AES-256-GCM or equivalent; never plain
AES-CBC, never a bare hash).

- The plaintext key never leaves the service layer. API responses return a
  masked form (last four characters), never the key itself.
- Decryption happens at the moment of the provider call and the plaintext is
  not retained.
- **Operator-facing consequence that must reach the deployment docs**: losing
  the encryption secret makes every stored credential permanently
  unrecoverable. It is not derivable from the database.

## Model catalog storage

Catalog metadata (context window, output limit, modalities, capabilities) comes
from models.dev, but `ollama`, `vllm`, `llamacpp`, and generic OpenAI-compatible
relays are absent from it — exactly the self-hosted long tail. Research:
`.trellis/tasks/08-31-providers/research/model-metadata-sources.md`.

Therefore:

- Every metadata field is **nullable and overridable per model row**. Do not
  model it as a foreign key into an immutable catalog table.
- Keep catalog-sourced values distinguishable from user-entered ones (a
  `source` discriminator, or separate columns). Otherwise a catalog refresh
  silently clobbers the operator's hand-tuned values — a bug that surfaces
  weeks later as "why did my context limit change".
- Store `fetched_at` so the UI can tell the operator how stale the catalog is.

## Forbidden

- String-interpolated SQL. Use Drizzle's query builder, or `sql` with bound
  parameters.
- `db` imported outside `src/server/`.
- Queries in Route Handlers.
- `SELECT *` into an API response. Project explicitly; it is how key columns
  and password hashes escape.
- Cascading deletes on message data without an explicit product decision.
